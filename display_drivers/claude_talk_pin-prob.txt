⏺ Good. Here's a summary of what was found and fixed:

  ---
  Root cause in driver.py: The PIO program pio_16wr uses set(pins, 0/1) instructions to pulse WR, which require set_base to be configured. The StateMachine()
  was passed sideset_base=self._wr instead. Because the program has no sideset_init, MicroPython's asm_pio_get_pins() computed count=0 for the sideset config,
  so pio_gpio_init() was never called for GPIO18 and SET_COUNT stayed 0 in the SM's PINCTRL — making every set(pins, ...) a no-op. WR never pulsed, nothing was
   ever latched by the display.

  Fix: sideset_base=self._wr → set_base=self._wr in driver.py's StateMachine() call.

  Additional change in nt35510.py: Default rd=26 → rd=40. GPIO26 is the SDIO D0 pin (sdio_rp2350_config.h: D0=26), so using it as RD would silently break SDIO
  if both were active. GPIO40 matches the PIO driver's default and avoids the conflict.

  The "works after PIO first" behavior was explained by this same bug: nt35510_pio.py properly initializes the display (its sideset-based SM is correctly
  written), and after that the display was already in a live state that masked driver.py's failure to re-initialize it.

✻ Worked for 36m 24s

※ recap: Fixed a PIO config bug in driver.py where sideset_base was passed instead of set_base, preventing WR from ever pulsing. Also changed nt35510.py's rd
  default from GPIO26 to GPIO40 to avoid SDIO conflict. Ready to test on hardware. (disable recaps in /config)
